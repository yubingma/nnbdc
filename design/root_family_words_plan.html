01背景与结论

用户提问：既然已经有了「形近词」词表，能否照此思路再做一个「同根词」词表？

结论：可以做，而且比形近词更简单，但必须换一套骨架 —— 不能照搬形近词的算法思路。

  • 形近词是「算出来的」：无数据依赖，靠编辑距离 + 长度分桶 + isolate 簇式排序动态生成，覆盖 100% 的词。
  • 同根词是「查出来的」：词根归属是词源事实，只能来自 cigen_word_link 现成数据；本地已有该表、已随系统数据同步，不需要新增表、不需要改服务端、不需要 isolate 排序。
  • 代价是覆盖率有限：全库只有 7.5% 的词有词根关联，落到单个用户的学习词书上约 10%–12%。这是本次方案最需要正视的约束，已在下节实测。

形近词和同根词是互补而非重复的两个维度：形近词治「拼写像、意思不像」的混淆，同根词治「一个词根认一串词」的推演记忆。两者入口并列放在「专项突破」板块是合理的。

03与形近词的本质差异

维度形近词（已上线）同根词（本方案）
数据来源纯本地算法：编辑距离 ≤1 + 同长度 + ≥3 字母本地数据表 cigen_word_link + cigen
覆盖率100%（任意拼写都成立）约 10%（数据边界）
准入逻辑需要 selectConfusableNear 过滤 + 长度分桶剪枝一次 join 查询即可，无需算法
排序需要 isolate 簇式排序（贪心、归属、防接龙）不需要排序 —— 天然按词根分组
分组语义簇头 = 学过的锚点词，组内同长度组头 = 词根本身（不是单词），组内长度各异
组的呈现无组头，仅靠连续组号着色必须有组头行（词根拼写 + 分类 + 中文含义）
一词多组不存在（每词最多一个锚点归属）存在：739/4,626 词（16%）挂 2 个以上词根
需要 isolate是（排序耗时可到秒级）否 —— 数据量小，主 isolate 内直接完成

差异集中在一处：同根词表必须自己造「组头行」。这是本次唯一需要碰 word_list.dart 的原因。

04方案设计

4.1 词表集合构造

B = 学习范围去重单词集合            // learning_dicts → dict_words，与形近词同口径
G = { 词根 c | c 在 B 内有 ≥2 个关联词 }   // 剔除孤立组（1 词组无对照价值）
词表 = [ 组头(c) + c 在 B∩关联 内的全部词 ]  按 G 排列
入口计数 = |G|（组数，与形近词「N 组」口径一致）
  • 范围口径与形近词完全对齐（学习词书并集），便于两卡片并列理解；
  • 孤立组（只有 1 个关联词）直接剔除：单张卡片无对照意义，正是数据里那 156–209 个；
  • 组内不做 maxCount 截断（区别于详情页的 20 词上限），词表页要完整呈现一族。

4.2 组头行的构造（关键设计）

复用 WordListPage 既有的分组渲染：groupOfWord 返回组号，连续同组号自动画成一张卡（top/middle/bottom/single），并支持按组号着色 —— 形近词已经验证过这套机制。

同根词把组头本身也作为一行数据放进列表，组头行与组内词共用同一个组号：

prospectn. 前景；展望

组头带分类标签、词根拼写、中文含义与词数；成员行沿用现有单词行样式

组头行用一个带前缀标记的虚拟 WordVo 承载（如 id = 'cigen:<cigenId>'，spell = 词根拼写），这样：

  • 组头的 groupOfWord 返回自己的组号，天然成为该组首行，无需改分组机制；
  • word_list.dart 的 renderWord 识别该标记后走专用组头渲染（纯展示，不进详情页）；
  • 成员行完全复用现有 WordItem 渲染与进度/发音等能力。

实现修正（真机反馈后已落地）：组头行首版把「词根 + 含义 + 词数」平铺在一行，先后暴露两个问题 ——

① 溢出：真机报 RenderFlex overflowed by 9.8 pixels，长词根条目（如 ab, ac, ad, af… 这类合并前缀）下各元素最小宽度之和超过卡片宽度。

② 省略号过早 + 中间留白：词根也参与弹性分配时，剩余空间被词根与释义各分一半，释义被压到 125px（375px 屏），右侧却还空着 54px —— 释义过早省略、又不靠右。

最终宽度分配规则：词根不参与弹性分配（按自身宽度完整显示，仅在超过可用宽度 40% 时才收缩省略）；其余全部空间由释义独占（放得下就完整显示、确实放不下才省略号）；词数用固定宽度列右对齐，无论词根/释义多长都贴着行尾。实测 375px 屏：词根 71px 完整、释义拿到 179px、词数右边界与内容右边界齐平。

同时把组头提取为独立组件 RootFamilyHeaderItem + 纯函数 buildRootFamilyHeaderContent，以便用窄宽约束（320 / 240px）与 RenderParagraph.didExceedMaxLines 直接做布局契约与溢出回归测试；卡片外壳仍复用 WordListItemLayout（新增 headerContent 入口），不重复边距/圆角/分组分割线样式。

实现修正（真机反馈后已落地）：最初把组头做成「列表里的一行虚拟 WordWrapper」，结果它被当成数据行 —— 随身听按索引取词时会播放词根行，序号也把它算了进去。

根本修正：组头不再是数据行。provider 只返回真实单词，组头改由渲染层在「每族首词前」插入（groupPosition: top，首词改 bottom 保持卡片连通）。于是序号 = 纯单词序号、随身听播放序列 = 纯单词序列、书签索引 = 纯单词索引，全部自然正确，无需在各消费侧加 skip 逻辑。

回归防线：测试断言 result.rows 中不得出现任何 cigen: 前缀行，组头一旦回到数据行立即失败。

4.3 只读语义（与形近词保持一致）

沿用形近词那一套已验收的只读约束，零新增设计：

  • getSortAlg() 固定 WordSortAlg.original（避免触发控制器 TSP 分支）；canCustomizeSort = false（隐藏排序菜单）；hasUnits = false；
  • 书签用内存态（返回词表可恢复位置，但不写 book_marks、不产生 DbLog、不触发同步）；
  • 覆写 masterWord / unmasterWord / deleteWord 为提示性 no-op；
  • 点词进详情页正常可用（详情页本身能展示该词的词根与释义）；组头行不可点。

实现修正（已落地）：原方案写的是「书签内存 no-op（恒返回 null）」。控制器在书签为空时会在首帧自动保存，恒返回 null 会导致反复保存，故实现为内存态书签——不落库的同时保持会话内位置恢复，语义与「纯浏览视图」一致。

4.4 一词多根的归属规则

16% 的词挂多个词根。为保持「一个词在词表里只出现一次」，需要一个确定性的唯一归属规则。拟定优先级：

  1. 成员数多的词根优先（大族吸收，家族感更强）；
  2. 成员数相同 → 分类优先级 ROOT > PREFIX > SUFFIX（ROOT 语义最强）；
  3. 仍相同 → 词根拼写字典序（保证确定性、可测）。

单词详情页的「词根」Tab 不受影响，仍展示该词的全部词根；词表只是选一个主族呈现。

实测影响（已用生产库对照验证）：唯一归属会让少数因冲突而降为孤立的组消失。对学习范围 39,799 词的真实用户：组数 740 → 657（−83），入表词数 3,897 → 3,826（−71，约 −1.8%）。代价可忽略，换来的是「每个词只出现一次、列表干净」。

4.5 缓存与计数

  • 入口计数取组数 |G|（与形近词「N 组」一致），由 getWordLists() 提供；
  • 内存缓存（key = userId）存「分组结构 + 签名」，列表与计数共用，避免 getWordLists() 被拖慢；
  • 签名 = 学习词书 dictId 有序集 + 签名哈希（范围为全库性质，用 关联行数 + 词根数 + 组数 的哈希即可，无需把数万 wordId 拼进签名）；
  • 轻量统计路径：关联表仅 5,415 行，直接全量取出后在内存与范围集合求交，不查 4 万行的范围词表，保证词表页刷新开销可忽略。

4.6 数据流与同步

全部为本地只读查询（learning_dicts / dict_words / cigen_word_link / cigens / words / meaning_items）：不落库、不产生同步日志、不改服务端、不新增表。

落地时对推荐项做了两处工程修正（均为实现细节，不改变上述产品语义）：

  • 组大小上限：最大族 45–46 词（fac）。当前不截断，完整呈现；若嫌长可后续加折叠。

07风险与明确不做

7.1 风险

  • 覆盖率预期管理（主要风险）：约 10% 的学习词能进词表。需在产品文案上避免暗示「全量同根词」，否则用户会认为功能残缺。
  • 词根数据质量：PREFIX 合并条目与个别误挂，会呈现为「同一族里词义跳跃」。属既有数据问题，本次不修（修数据应走 AdminCigenOptimizeController 的 AI 清洗链路，是独立任务）。
  • 组头行对框架的影响：这是唯一需要碰 word_list.dart 的点。因为组头是框架内的虚拟数据行，需确认不影响既有的「单元标题仅 DictWordsProvider 渲染」「孤立组紧凑重编号」等逻辑（形近词的组号重编号逻辑可照抄）。
  • 缓存失效：范围变化（增删词书）与词根数据升级（sys_db_version 变化）都需触发重算；词根数据带版本，签名纳入版本号即可。

7.2 明确不做

  • 不用拼写规则（isSameWordFamily）派生词族 —— 它是为「干扰项排除」设计的宁可漏判策略，拿来做词表会大量误并（corner/corn、mother/moth、flower/flow）。
  • 不新增数据库表、不改服务端、不动同步链路。
  • 不补词根数据（不给 important 这类词补关联）。
  • 不做组内学习（不进学习轨道）、不做词根详情页。
  • 不改动形近词的任何现有行为。
