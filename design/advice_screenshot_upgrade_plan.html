按用户组织会话 · 对某一条请求引用回复 · 聊天中上传截图 ｜ 出稿日期 2026-10-12
一句话结论：你要的三件事都成立，而且第二件（对某一条请求回复）和第三件（聊天中发截图）在现有代码里都有能直接复用的底子，不需要新建大表或新开上传通道；第一件（按用户组织）要改的是服务端的取数方式（现在一次拉全量、平铺），不是界面画法。

一、我是怎么理解你的需求的

你打开的是管理端的「意见建议」，看到的是一条消息一张卡片的长列表，于是有三个不舒服的地方，我逐条对应到你要的动作：

你的话我理解成判断依据
「按照用户来组织，把一个用户的所有聊天内容收在一起」 管理端首页从消息列表改成客服会话列表（组织维度）：一个用户一行，显示最后一条内容、时间、未读数、含需求的条数；点进去才看这个人和客服的完整聊天 现在 app/lib/page/admin/feedback_management.dart:518 把 Advice 消息一张一张平铺；同一个人今天发的三条意见就是三张卡片。点进去之后的聊天记录其实已经是按人聚合的（同文件 :1237 调 getLastestMsgsBetweenUserAndSys），缺的只是"首页这一步"
「用户往往会在聊天过程中多次提出多个请求，希望直接对用户的某个请求进行回复」 回复不再是"对着这个人发一句话"，而是挂在你选中的那一条用户消息上；用户端看到这条回复时，气泡上方带一个引用块，明确显示"这是在回你哪一句" 用户端 app/lib/page/msg.dart 是自由聊天：用户想说几条就说几条，一条一条发。管理员现在的回复（app/lib/page/admin/feedback_management.dart:1635 的 replyAdvice）和用户原话之间没有任何指向关系，两句不同的请求被一句笼统回复盖住，用户根本对不上号
「希望在聊天过程中支持上传截图」 「意见建议 / 客服」的输入框旁边加一个加号：能从相册选、能直接拍照、一次最多几张，发送时把图一起发上去，用户端和管理端都能在气泡里看到这些图 现在只有单词报错能带图（app/lib/page/bdc/dialogs/bdc_dialogs.dart:891 走 uploadImg，服务端 server/nnbdc-service/src/main/java/beidanci/service/bo/ErrorReportBo.java:69 把图名拼进意见正文）；客服聊天本身一个字都没提图片，用户想发截图没有入口

先说一个必须分清的坑：项目里「意见」有两套数据

客服会话（msg）和需求（feature_request）是两套东西，不要混。
  • 用户在「意见建议 / 客服」（app/lib/page/me.dart:1967 入口 → app/lib/page/msg.dart）说的话，落在 msg 表，类型是 Advice。
  • 用户在「需求墙 / 功能投票」（app/lib/page/me.dart:2152 入口 → app/lib/page/feature_request_wall.dart）发的需求，落在 feature_request 表，带点赞（vote）和举报（report）。
  • 两者之间唯一的桥，是管理员在客服会话里给某条消息打一个「需求」标签（server/db_upgrade/v74_add_tag_to_msg.sql，界面 app/lib/page/admin/feedback_management.dart:804），然后按这个标签筛出来看。
本方案只动客服会话这一套（你说的"聊天内容"就是它）；需求墙（app/lib/page/admin/feature_request_management.dart）不动。这一段已经按项目规矩补进了 doc/glossary.md 的 4.6 节。

二、现状：一次点评一条消息，是怎么走完的

  1. 用户在 app/lib/page/msg.dart:133 调 sendAdvice.do；InputBar 里只有文字这一个入口，没有选图入口（输入区画法见同文件 :377）。

2.2 管理员点开一条消息之后

  1. 先把这条置为已读（app/lib/page/admin/feedback_management.dart:592）。
  2. 拉这个用户和系统的最近 50 条聊天（同文件 :1237），其中发给客服的未读一起置为已读（:1256）。
  3. 底部输入框发一条回复（同文件 :1626），服务端 MsgBo.replyAdvice（server/nnbdc-service/src/main/java/beidanci/service/bo/MsgBo.java:313）写一条 AdviceReply，并通过长连接把未读消息数推给用户。

3.2 需求的粒度：标记在消息上，不是会话上

这一点按你的意思定死：会话列表只是组织骨架，需求是贴在消息上的。一次会话里用户说了五件事，其中两件是需求，那就只标记那两条消息——这也正是 msg.tag 现在的语义（server/db_upgrade/v74_add_tag_to_msg.sql 的字段注释：「管理员业务标注标签（如：需求）」），已经建了索引 idx_msg_tag，基座是对的。

视角拿什么组织怎么用
会话列表（管理端首屏） 一个用户一行 当作导航用。行上标两个小数字：未读几条、含需求几条。点需求数字直接跳进会话并定位到那条带需求标记的消息
需求列表（管理端新的一屏） 一条带需求标记的消息一张卡 当作待办用。卡片直接显示是哪位用户在哪次对话里提的那一句，点进去落在那条消息上并高亮，带着上下文回复。处理完就取消标记，它从这张列表里消失

这样两个视角各干各的事，而且都是消息粒度：需求列表不是"这个人提过需求"，而是"这一句是需求"。顺带一个好处——某个用户今天又发了一条无关的新消息，也不会把他那条老需求顶到需求列表最前面。

3.3 需求列表怎么落（服务端）

  • 查询很简单：msg.tag = '需求'，按消息时间倒序。索引 idx_msg_tag 现成。
  • 既然它是一张真正的需求待办列表，就给消息级需求补一列状态 req_status（投票中 / 开发中 / 已拒绝 / 已完成，四档与需求墙的文案一致），默认 投票中。界面按状态分栏，和需求墙的用法一致，不用另学一套。
  • 接口：一个按状态取需求列表、一个改状态；setMsgTag.do（server/nnbdc-service/src/main/java/beidanci/service/controller/MsgController.java:201）继续负责贴/取消标记，不做状态的事，两件事分开、互不牵扯。
  • 会话摘要接口里顺带算一个"含需求条数"，就是同一次查询里 COUNT(*) FILTER (WHERE tag = '需求')，不额外发请求。
已删除消息上的标记必须有交代。 现在"清理旧反馈"（server/nnbdc-service/src/main/java/beidanci/service/bo/MsgBo.java:395 的 cleanupOldAdvice）只保护打了标记的消息，所以带需求标记的消息不会被清掉，这是好事。万一有别的路径把原文删了，需求列表里的这条要直接标成「原消息已删除」并提供一键清除标记，不允许静默少一条——列表条数与库里条数对不上，是最难查的那种问题。

3.4 消息级需求与需求墙（feature_request）的关系

两套数据保持独立，但管理端的需求入口一屏看两边，每条用来源标签区分，点击时去各自的处理位置：

  • 来源「客服会话」→ 你在聊天里标的那条消息；点击落到会话里那条消息上，回复走引用回复，处理完取消标记。
  • 来源「需求墙」→ 用户自己发的 feature_request；点击进需求墙管理（app/lib/page/admin/feature_request_management.dart），走点赞数与状态流转那一套。
  • 建议：因为两边状态档位一致（投票中 / 开发中 / 已拒绝 / 已完成），在列表里合并展示不会让管理员犯迷糊；真正改状态时各走各的接口。

3.5 服务端：新增一个"按用户取会话"的接口

现在管理端拿数只有一条路：全量拉 Advice（server/nnbdc-service/src/main/java/beidanci/service/bo/MsgBo.java:378）。改为新增一个会话摘要查询，用一条 GROUP BY 把人聚起来：

  • 分组键：from_user_id（提意见的人）。
  • 每个会话返回：用户 ID、昵称、头像、最后一条内容、最后时间、未读条数、总条数、含需求条数、是否永久会员。
  • 排序：有未读的在前 → 最后时间倒序。
  • "最后一条内容"要顺带标出是不是纯图片（界面上写成 [图片]），别让管理员点开才发现没字。

接口按 MsgController 现有写法补一个即可（server/nnbdc-service/src/main/java/beidanci/service/controller/MsgController.java:119 那个位置旁边）。原来的全量接口先留着不删：老版本客户端还要用，等新版铺开再清理。

3.6 服务端与协议：让回复挂到具体一条消息上

只加一层引用，不做多层嵌套——这是奥卡姆剃刀：能满足"我在回你哪一句"就够了。

  1. msg 表加一列 reply_to_id（可空，指向被回复的那条消息），升级脚本放 server/db_upgrade/，表名与字段注释按项目规矩写全中文 COMMENT。
  2. server/nnbdc-service/src/main/java/beidanci/service/po/Msg.java 与 MsgVo 同步加字段；查聊天记录时顺带把被引用消息的正文与发送者一起带上，让客户端一次就能画出引用块，不必再发一次请求。
  3. replyAdvice.do（server/nnbdc-service/src/main/java/beidanci/service/controller/MsgController.java:133）多收一个可空的 replyToId。
  4. 快速失败：如果传上来的 replyToId 查不到，直接返回失败并说明"被回复的消息不存在"，绝不悄悄落一条没有引用的回复。
  5. 删除要有交代：现在删消息是裸删（server/nnbdc-service/src/main/java/beidanci/service/bo/MsgBo.java:412）。如果那条消息已经被回复引用，删除前直接拒绝并提示"请先删除引用它的回复"，而不是删完留下一条指向空气的引用。

3.7 聊天中发截图：复用上传接口，但不许再压成正方形

环节做法
客户端选图 输入区加号 → 弹「拍照 / 从相册选择」，按来源申请相机或相册权限（image_picker 项目里已经在用，见 app/lib/page/bdc/dialogs/bdc_dialogs.dart:776、:818、:833 的写法），一次最多 3 张，发送前在上方排缩略图、可单张删掉
上传 复用现成的 uploadImg.do（app/lib/api/api.dart:492），只多传一个目录：新增 dir=advice，落到 …/img/advice/。整条上传链路（格式探测、文件名生成、目录创建）都已经具备，不需要新通道
尺寸 上传参数从"正方形 size"改成"长边上限"（建议 1080），等比缩放。这一条同时修掉 3.4 上面说的报错截图变形问题

两端展示 用户端 app/lib/page/msg.dart 与管理端 app/lib/page/admin/feedback_management.dart 的气泡都要能渲染图片：横排缩略图 + 点击看大图（管理端已有大图预览，:873 与 :1183，直接复用）

3.8 顺手根治：图片名的解析只留一份

同一个 【报错图片】 标记，现在在管理端被写了两遍：app/lib/page/admin/feedback_management.dart:45 与 :1131，连"剥出纯文本、解析图片名"这套逻辑也是两份（:63 与 :1145），再加上 :16 那个会拼错地址的 _resolveImgUrl。这次一改格式，就是三处一起改，漏一处就出线上问题。

建议抽一个通道工具文件（例如 app/lib/util/advice_content.dart）：解析、剥离、拼地址三件事各一个函数，客服聊天相关的页面全部调它。既符合"一处定义"，也不增加新概念。

3.9 未读计数与权限

  • 未读数：现在红点走的是"发给系统账号的未读消息总数"（app/lib/page/admin.dart:241 → getMsgCounts.do），并不专门限制在客服会话上。改成会话摘要里的未读合计，红点数字才和首屏列表对得上。
  • 上传配额：uploadImg.do 目前只判断"是不是登录用户"，没有任何频率约束。随这次一起加一个按用户的上传上限（建议 50 张/天），避免有人拿它当免费图床。

四、这次不做的事（明确写出来，免得后面又变成"顺手加"）

  • 不给图片加内容审核。客服会话是内部处理通道，图片只有管理员看得到，不对外展示；等哪天截图要展示给别人看，再单独讨论审核。
  • 不做会话级删除 / 归档。现有的"按天数清理旧反馈"（app/lib/page/admin/feedback_management.dart:155 → MsgBo.cleanupOldAdvice）继续用。
  • 需求墙的投票与举报机制不动（feature_request 的 vote / report、用户端需求墙）。这次只把「被标记为需求的那条消息」正式做成一张待办列表，并把两边的需求在同一屏里看得见。
  • 不做多层引用嵌套，只允许一层。
  • 不扩展标签体系。字段 msg.tag 保持单值语义，这次只从界面提供「需求」这一种标记，其它标签（比如"问题 / 待跟进"）等真的需要再说，不提前铺开。
  • 不做"标记整个会话为需求"。需求只贴在消息上；一个会话里哪几句是需求，就标记哪几句。
  • 管理端不整体重画。首屏换成会话列表、详情里加引用块和图片渲染，沿用现有配色与卡片写法，不重做视觉体系。

五、工作量与验证口径

阶段内容怎么算做完了
一、服务端会话摘要接口 + 消息级需求列表与状态接口 + reply_to_id 与 req_status 两个升级脚本与实体字段 + replyAdvice 收引用参数 + 删除拒绝规则 + 上传等比缩放与配额会话按用户返回、需求列表按状态返回、未读数对得上库；传了不存在的引用 ID 会明确报错；需求条数与库里一致
二、客户端（两端）管理端改会话列表 + 需求列表两屏、会话详情里长按操作与引用块；用户端输入区加选图与图片气泡；解析抽成一份共用真机跑通：发文字 + 发图 + 对某条引用回复 + 标记某条为需求并从需求列表点回原文，两端气泡、引用块、缩略图、定位高亮都正常
三、回归单词报错带图那条老链路（app/lib/page/bdc/dialogs/bdc_dialogs.dart:891）不能被改坏报错带图仍能上传、管理端仍能显示

粗估：服务端一天（多出需求列表与状态这一块），两端客户端一天半，联调与真机回归半天，合计约三天。真正容易踩的是图片路径拼接、等比缩放、以及从需求列表跳回原文时的定位这三处，都在上面点名了。

六、需要你确认的三件事

  1. 消息级需求要不要带状态。 我按"要"来做：给打了需求标记的消息补一列 req_status（投票中 / 开发中 / 已拒绝 / 已完成），这样需求列表才是一张能推进的待办，而不是一堆标记。建议：要。若你希望更轻，就只保留标记、用"处理完取消标记"表示结束，那样省一列但看不到"这个需求承诺了却没做"。
  2. 需求列表和需求墙要不要并成同一个列表。 我按"同一屏、两条来源"来做：来源「客服会话」的落到聊天里那条消息，来源「需求墙」的进需求墙管理。建议：合并展示、分开处理。两边状态档位一致，管理员看一屏就够，不必在两个入口之间来回切。
  3. 会话详情里"引用回复 / 标为需求"怎么触发。 我按长按消息弹操作菜单来做，同时保留卡片上现有的「回复」按钮（app/lib/page/admin/feedback_management.dart:779）方便直接发现。建议：长按为主、回复按钮保留。

7.2 实现时与方案有出入的三处

  1. 图片标记只在服务端拼一次。 方案里说两端各自把 【报错图片】 拼到正文末尾。真做的时候发现那样等于把同一条协议写两遍，任何一边改了写法就静默错位。所以改成：两个接口都收可选的 imageFiles，由 MsgBo.appendImageFiles 统一拼装，客户端只负责把路径交上去。
  2. 从需求待办跳回原文，用"先估算再对齐"两步定位。 目标是较早的消息时，列表还没把它构建出来，找不到它的位置；所以先按它在列表里的序号估一个初始滚动位置让它被渲染，再精确对齐到可见处。目标不在最近 200 条内时明确提示，不装作定位成功。
  3. 没有做上传配额。 方案里说加一个按用户每天 50 张的限制。实现时判断：真正的滥用者用脚本可以直接打别的接口，这个限制挡不住；而 uploadImg.do 目前对任何登录用户开放，加一条"看目录里文件数"的统计既不准（按文件名前缀数每天的文件）又增加一处需要维护的逻辑。这一条留给你决定要不要单独做，我没有顺手加。
  4. 截图是"相册多选、拍照单张"两条路。 相册一次最多补齐 3 张；拍照一次只能拍一张（系统相机接口本身就只回一张），想再来一张就再点一次加号。两端都按来源分别申请相机或相册权限，用户取消时什么都不发生。
