## 一、三条硬规矩

1. **术语优先**：本表有条目的概念，只能使用「标准叫法」，不能一会儿一个同义词（例如同一个东西一会儿叫"词书"、一会儿叫"词库"）。
2. **首次出现带代码标识**：写成 `词书（dict）`；同一段落内第二次出现就只用「词书」。
3. **禁止裸代号**：字母、符号、缩写都不能单独承载信息，必须配一句人话。

## 二、表达格式规范（治"听不懂"的具体毛病）

### 2.1 禁止裸用字母代号

**真实反例（我过去发给你的原话）**：

> E/F 闸门边界收口 → G（服务端死常量 GRADUATION_STABILITY=180、app/test_fsrs.dart 硬编码 180、repair 里残留的 stability >= 掌握线 代理判据）→ ⚪ 清理（删 app/fsrs_test.dart 那份含旧 bug 的实现、clean_db.sql 补 learning_logs）→ H 只出数据与方案不擅改阈值。

这句话你要同时猜四件事：E 是什么？F 是什么？G、H 从哪冒出来的？`⚪ 清理` 到底是"要清理"还是"不用清理"？

**根因**：这些字母只在上一轮对话的那张清单里存在过。隔一天、或换个话题回来，它们就全部失效。

**规矩**：

- 字母代号**只在同一轮回答内**可用，且该轮必须已经给出过带字母的清单。
- 任何时候**首次**提到某个条目，必须写「字母（一句人话摘要）」。
- **跨轮、跨文档**引用时禁止只用字母，必须重述摘要。

**关于文档内部的编号体系**：项目现有若干编号写法 —— `P0-1`（优先级）、`D1`（决策点）、`B1`–`B6`（代码位置表）、`阶段 5`、`Task 2`、`3.C`（拿章节号当指针）。**这些可以在同一份文档内使用**，前提是那份文档里已经列出过完整清单；但一旦换到对话里或换到另一份文档，编号立即失效，必须重述内容。

**同一件事的人话版**：

> 掌握线（判定单词算不算"已掌握"的门槛）目前只由客户端 `app/lib/constants.dart:54` 定义，值是 120。但服务端 `server/nnbdc-util/src/main/java/beidanci/util/Constants.java:9` 还留着一个 `GRADUATION_STABILITY = 180.0`，整个 Java 代码库没有任何地方引用它；`app/test_fsrs.dart:22` 也硬编码了 180。这两处 180 属于死代码和过期副本，会让人误以为掌握线是 180。建议删掉，让掌握线只有一个来源；是否删、以及定 120 还是别的值，由你决定，我不擅自改。

### 2.2 状态符号（固定含义，禁止自行发明）

| 符号 | 含义 | 使用场景 |
|---|---|---|
| 🔴 | 严重 | 会导致功能不可用或数据错误，必须优先处理 |
| 🟠 | 中等 | 特定场景出错，或体验明显受损 |
| 🟡 | 待确认 | 存疑、遗漏、需要你拍板 |
| ⚠️ | 警示 | 与代码不符、有风险；用在表格单元格里表示该数值为 0、疑似缺失 |
| ✅ | 事实 / 完成 / 通过 | 已核实为事实、已完成；审查表里大量写作「✅ PASS」 |
| ❌ | 错误 / 未完成 | 已核实为错误，或未完成 |
| ⏳ | 进行中 | 预防性定义。目前实践里状态是用文字写的（如「状态：待架构审查」） |
| 🟢 | 已修复 | 预防性定义，目前实践里用文字写状态 |
| ⚪ | 建议 | **已弃用** —— 太弱，容易被误读成"可选不办"。今后一律写成「建议（可选）」 |

**规矩**：

- 符号必须与一句话说明同时出现；禁止只丢一个符号让你猜我的态度。
- 状态符号只用上表这几个。`💡 🎯 🔥 🚀` 属于装饰，不承载状态信息，不得用来表达结论。
- 箭头类字符一律统一成 `→`，`->`、`➔`、`⇒` 视为错写。

### 2.3 箭头链 `A → B → C`

**反例**：`E/F 闸门边界收口 → G（…）→ ⚪ 清理 → H 只出数据与方案`

箭头把「因果」和「先后顺序」压成一行，省掉了主语和逻辑连词，读起来像密码。

**规矩**：

- 箭头链**最多 3 环**，每环必须是一个完整短句（有主语、有动词）。
- 表达**因果**用「因为…所以…」；表达**先后**用有序列表 `1. 2. 3.`。
- 箭头只用来表示**同一个值的流向**，例如 `客户端 version → 服务端 version`。
- **状态流转链同样受 3 环限制**。反例（4 环，超限）：`已通过架构审查 → 已获用户审批 → 执行完成（阶段 3-5）→ 待用户决策（阶段 6）`。改写成有序列表即可。
- `↔` 只表示「配对 / 对应」关系，且必须配文字说明，例如 `客户端 learning_word ↔ 服务端 learning_word`。

### 2.4 其他表达红线

- 一句话最多 1 处括号补充。上面的反例套了 3 层括号，这是重灾区。
- 指代文件必须给全路径 + 行号：`app/test_fsrs.dart:22`，不能写「那个测试文件」。
- 指代数值必须写全：`180`，不能写「那个阈值」。
- 描述业务动作时禁止用「收口 / 收敛 / 对齐 / 拉齐 / 闭环 / 链路 / 闸门 / 心智 / 抓手」，第三章给了替换说法。
- **已弃用的说法**：**「词库」**→ 改用「词书」或「通用词典」（见 6.5）；**「易混淆词」**→ 改用「形近词」（见 6.6）；**「卡姆剃刀」**→ 改用「奥卡姆剃刀」（见 3.2）。
- **结论先行**：先一句话说结论，再给证据。
- **默认精简**（2026-09-30 用户反馈后加入）：能一行说完就不写三行；不复述你已经知道的内容；一次最多问 3 个问题。需要你决策的事，一律**先给我的建议**，让你可以只回一个「同意」。
- **少问**：技术细节由我按项目既有规范自行判断并承担，不要把我该拿的主意摊给你。

### 2.5 我每次回答前要过的自查清单

1. 有没有裸字母代号？
2. 有没有符号没配文字？
3. 有没有用到第三章的黑话？

## 三、黑话 → 人话对照表

### 3.1 工程黑话

| 我可能会说 | 说人话 |
|---|---|
| 幂等 | 同一件事做一次和做十次，结果一样，不会重复计数、重复写入 |
| 兜底 / 托底 | 出问题时额外加一层保险。**本项目规矩是尽量不用**，见第五章 |
| workaround / 权宜之计 | 绕开真正原因的临时补丁。**本项目禁止** |
| 根治 | 找到并消除问题的真正原因，而不是让症状消失 |
| 收敛 | 数值或状态稳定下来、不再乱变；也指把多种情况统一成一种 |
| 发散 | 越跑越乱，结果不可控 |
| 回归 / 回归测试 | 改完代码后重跑原有测试，确认没把旧功能弄坏 |
| 脏数据 | 不符合业务规则的错误数据，例如主键超长、表名写成复数 |
| 自愈 | 程序自己偷偷修掉错误数据。**本项目禁止**，因为会掩盖根因 |
| 状态机 | 用一组明确状态和允许的跳转来描述流程，而不是散落各处的 `if-else` |
| 链路 | 一次操作经过的完整环节：客户端 → 接口 → 数据库 |
| 闭环 | 从发起到验证结果都做完了，没有悬空的一半 |
| 口径 | 同一个指标的计算规则。例如打卡率的分母是"注册至今总天数" |
| 对齐 / 拉齐 | 让两处的说法或取值一致 |
| 裸奔 / 裸写 | 缺少必要的保护或引号。例如 PostgreSQL 保留字 `user` 不加双引号 |
| 架空 | 名义上存在但实际不生效。例如年级子分组里没有书，等于被架空 |
| 死常量 | 直接写死在代码里的数字（如 180），改一下就得动代码 |
| 代理判据 | 用另一个间接指标代替真正的判断依据，例如用 `stability >= 180` 代替"已掌握" |
| 残留 | 旧逻辑没删干净，还留在代码里 |
| 静默失败 | 出错了但不报错、不留日志 |
| 快速失败 | 一有问题立刻报错暴露，而不是继续跑下去 |
| 颗粒度 | 划分的粗细程度 |
| 契约 | 两端约定好的数据格式与含义 |
| 不变量 | 任何时刻都必须成立的规则 |
| 旁路 / 透传 | 数据不经过处理直接过去 / 绕过正常通道 |
| 降级 | 功能出问题时退到简化版本继续可用 |
| 漂移 | 两处本该一致的东西慢慢变得不一致 |
| 竞态 | 两件事同时进行，先后顺序不定，结果不可预测 |
| 下沉 | 把逻辑从上层挪到更底层共用 |
| 重构 | 不改外部行为的前提下整理代码结构 |
| 编排 | 把多个步骤安排成一条执行流程 |

## 四、业务领域术语

### 4.1 词书与单词

| 标准叫法 | 代码标识 | 人话解释 | 注意 |
|---|---|---|---|
| 词书 | `dict` | 一本可以背的书，如「四级词汇」「人教版七年级上册」 | 「词库」已弃用（见 6.5）；「通用词典」是另一回事 |
| 通用词典 | `dict`（`Constants.COMMON_DICT_ID = "0"`） | 全库公共释义来源，不属于任何分类 | 词数随导入变化，具体数量请实时查库，不要引用旧数字 |
| 词条 | `dict_word` | 「某本词书里的某个单词」，带序号 `seq`、单元 `unit` | 复合主键 dictId + wordId |
| 单词 | `word` | 英语单词本身（拼写、音标） | |
| 释义项 | `meaning_item` | 一个单词某个词性下的具体中文释义，带热度 `popularity` | |
| 词书就绪 | `dict.is_ready` | true = 已冻结发布，禁止再改词条；false = 草稿导入中 | |
| 词书可见 | `dict.visible` | false = 软下线，前端词书列表看不到 | 游戏大厅取词忽略此字段，是已知缺陷 |
| 可编辑 / 可删除 | `dict.editable` / `dict.deletable` | 官方版权书为 false，自建书为 true | |
| 衍生词书 | `dict.base_dict_id` | 如「乱序版」基于「顺序版」派生，词条继承，只改呈现顺序 | |
| 选词排序 | `dict.sort_alg` | RANDOM 真乱序 / ALPHABETIC 字母序 / FREQUENCY 高频优先 | |
| 系统词书 | `dict.owner_id = Constants.SYS_USER_SYS_ID`（`'15118'`，用户 `sys`） | 官方词书，作者是系统用户 sys，其 ID 硬编码为 15118 | 生产库实测 761 本官方词书、NULL 为 0 本；v62 的错误说明已由 v67 修正 |
| 用户自建词书 | `dict.owner_id` = 用户 ID | 用户自己导入的书，可用 `is_shared` 发布共享 | |
| 释义过滤阈值 | `dict.popularity_limit`（默认 `Constants.DEFAULT_POPULARITY_LIMIT = 5`） | 用通用词典释义时，`popularity` **大于**该阈值的释义项会被自动隐藏（只留常见释义），避免释义过多干扰背诵 | null 表示不限制 |
