## 1. 业务痛点与破局理念

### 1.1 现状与马太效应死锁（The Matthew Effect Deadlock）
在 NBDC 的 UGC 体系中（单词配图 `WordImage`、例句及翻译 `Sentence`、助记/释义翻译 `WordShortDescChinese` 等），目前的排位规则是**纯基于用户点赞数（`hand`）降序排列**：
- **占坑先发优势**：上线早的平庸内容积累了数十乃至上百个赞，长期占据唯一的默认展示位；
- **新内容不见天日**：新创作者贡献的构思绝妙、画质精美、助记深刻的内容，初始点赞为 0，只能深埋于弹窗二级列表的最底部；
- **背词心流排斥翻页**：用户在做题背词时，首要诉求是专注心流与答题效率，几乎不会主动在每个单词后点击“查看更多”翻到底部给新内容投票；
- **恶性循环**：**“无曝光 ➔ 无投票 ➔ 永沉底 ➔ 创作者受挫停更 ➔ 内容生态板结”**。

### 1.2 核心理念：AI 星探 + 真实用户终审
用户提出的创意核心在于**引入 AI 打破死锁**：
- **AI 的定位不是终极法官，而是“星探与冷启动起跑加速器”**：
  - AI 负责在暗处为无人问津的新内容进行多维度专业质检与潜力打分；
  - 平台为 AI 评分高的潜力新星提供专属展示位（或动态混排流量）；
  - **最终生死权依然交给真实用户**：新内容拿到曝光后，接受真实用户的赞/踩检验，好内容在积累真实好评后“毕业”转正，坏内容被踩后迅速下架汰换。

## 2. 深度细节难点剖析与系统解法

用户敏锐地指出“这里面还有些细节难点”。结合本项目的端云架构、背词做题心流与算法成本，梳理出以下 **6 大核心细节难点** 与系统性解法：

```mermaid
flowchart TD
    A[用户提交新 UGC] --> B[异步审核: 合规 + AI质量评分]
    B --> C{是否合规且高分?}
    C -- 否/低分 --> D[沉淀于普通待选池]
    C -- 是/高分(≥8.0) --> E[进入冷启动新星池 (New Star Pool)]
    E --> F[动态混排展示: 80%高赞经典 + 20%AI新星]
    F --> G[真实用户做题交互]
    G -- 连续点赞(Net Hand≥5) --> H[🎉 毕业! 晋升为主榜成熟高赞]
    G -- 遭遇差评(Foot≥2) --> I[❌ 淘汰! 退出新星池降权]
```

### 难点一：如何精准界定“得不到展示机会”？（冷启动池边界）
- **核心问题**：如果简单以 `hand == 0` 来判定，会有致命漏洞：一条内容如果已经被 1,000 个人看过了但依然没人点赞（甚至被踩），说明它质量极差，绝不能再次作为“缺乏机会的新星”推给用户。
- **现状约束**：目前系统仅记录了投票事件（`Event` 表的 `hand`/`foot`），**没有记录全量的展现曝光次数（Impressions）**，短期内也不宜为每一次离线本地做题记 Log 上报展现日志（会造成巨量端云同步流量）。
- **极简工程解法**：采用**「时间衰减窗口 + 互动总数上限」**构成双因子冷启动保护期：
  $$\text{InColdStartPool} = (\text{now} - \text{createTime} \le 30\text{天}) \land (\text{hand} + \text{foot} \le 3)$$
  - 只有处于 30 天内且总互动数不超过 3 次的内容，才属于“冷启动探索池”；
  - 一旦互动次数超过 3 次，无论好坏，说明已被充分检验，自动退出冷启动池。

---

### 难点二：AI 评分的成本与触发时机（Cost & Timing）
- **核心问题**：全量扫描全库历史 UGC 成本高昂；若在每次用户请求时实时调用 LLM 打分，会严重拖垮响应延迟并带来不可预测的 API 账单。
- **极简工程解法（零额外开销 · 合并流水线）**：
  - 项目在 `WordImageBo.java` 中已经具备了 `asyncReviewImage` 的异步调用链路；
  - **“搭便车”策略（Piggyback）**：将「合规性审核」与「质量策展打分」合并为单次 LLM 请求，在用户上传新 UGC 后的异步队列中一次性完成：
    ```json
    {
      "approved": true,
      "ai_score": 8.8,
      "score_reason": "图片意象精准对应单词'candid'的坦诚、抓拍感，构图干净无水印，利于视觉记忆。",
      "dimensions": {
        "relevance": 9,
        "clarity": 9,
        "memorability": 8
      }
    }
    ```
  - **历史存量处理**：不搞一次性全库穷举，而是后台维护一个定时 Worker，仅对“用户正在背诵的高频词汇中零点赞的新内容”按需离线打分。

---

### 难点三：UI 呈现策略（奥卡姆剃刀：不打断极简背词心流）
- **核心问题**：如果为了展示 AI 推荐，在做题页面并列堆砌“高赞榜”、“AI 甄选榜”等多个 Tab 或卡片，会造成极严重的视觉噪音，违背项目的 [app-ui-aesthetic](file:///Volumes/ssd/ppdc/.agents/skills/app-ui-aesthetic/SKILL.md) 原则。
- **极简设计方案**：
  1. **做题主卡片区（隐式混排，零多余容器）**：
     - 主卡片展示的依然是一张图片或一条核心助记，绝不搞双图并排；
     - 若当前展示的是 AI 甄选的新星内容，仅在右上角以极其低调优雅的极简微胶囊标记呈现：`🌱 AI 甄选 8.8`；
  2. **展开全部 UGC 弹窗（二级界面）**：
     - 在弹窗顶部保留专栏：「🌟 潜力新星 (AI 评分 8.5+)」；
     - 下方紧随「🔥 经典高赞」；
     - 每一条新星卡片清晰展示 AI 的一句话简评（如：“巧妙运用谐音记忆法”），极大降低其他用户的辨识与投票门槛。

---

### 难点四：流量分配策略（探索与利用：Epsilon-Greedy）
- **核心问题**：如果 100% 展示 AI 推荐，老内容完全消失，且一旦 AI 出现“审美幻觉”（给糟糕的内容打了高分），所有用户都会被迫看到糟糕的内容；如果只展示老高赞，新内容依旧没流量。
- **工业级平滑方案（探索与利用算法）**：
  - **80% 利用（Exploitation）**：展示当前全库净赞最高（`hand - foot`）的经典稳妥内容；
  - **20% 探索（Exploration）**：若该单词存在冷启动池且 `ai_score >= 7.5` 的新内容，则有 20% 的做题几率将该新星注入为主展位；
  - **同用户防疲劳**：同一个用户当天若已经对某个新星进行了点赞或踩，后续不再重复探索该内容。

---

### 难点五：闭环转化：毕业与淘汰机制（防刷与反作弊）
- **核心问题**：AI 评分再高也只是预估，如何确保差内容不被霸榜，好内容能顺利融入大盘？
- **自洽流转规则**：
  1. **毕业机制（Graduation）**：
     - 当新星内容在专属位累积获得 **净赞数（hand - foot） $\ge 5$** 时；
     - 判定该内容已通过真实用户实测，自动将其标记为“已毕业”；
     - 移出冷启动专属展位，凭借自身的真实点赞数正式进入常规主榜单竞争，将展位空间腾给下一批新人。
  2. **快速止损汰换（Fast-Fail Eviction）**：
     - 只要新星内容在冷启动期收到 **$\ge 2$ 个踩（`foot`）**，或者在给足了 50 次探索展现后点赞数为 0；
     - 判定 AI 出现审美偏差或该内容不被大众接受，直接清零其冷启动权重，降权移入普通深层列表，防止劣质内容持续污染做题界面。

---

### 难点六：端云架构协同与离线一致性（Drift + sys_db_sync）
- **核心问题**：客户端采用本地 SQLite 运行核心背词主流程，如何将 AI 评分下发，并且在无网离线时依然能合理展示？
- **架构兼容落地方案**：
  1. **表结构升级**：
     - 在服务端的 `word_image`、`sentence` 等表，以及客户端的 Drift 数据表（`WordImages`、`Sentences` 等）中平滑补充 2 个轻量字段：
       - `ai_score` (Double, 可空)：AI 策展综合得分（0.0 ~ 10.0）；
       - `ai_reason` (Text, 可空)：AI 评语摘要（如：“形象生动，突出词根记忆”）；
  2. **日志增量同步**：
     - 服务端完成异步打分后，调用 `sysDbLogBo.logOperation(image, "UPDATE", ...)`；
     - 客户端在日常同步（`sys_db_sync.dart`）中自动将 `ai_score` 写入本地数据库；
  3. **客户端本地决策**：
     - 客户端本地查询词图时，直接通过本地计算：
       ```dart
       // 80% 取最高 hand，20% 尝试探取冷启动高分 ai_score
       final candidate = (random.nextDouble() < 0.2 && hasColdStartAiStar) 
           ? bestAiStar 
           : bestHandImage;
       ```
     - **离线零负担**：完全在本地 SQLite 完成毫秒级过滤与决策，无需依赖任何在线实时推荐接口。

## 3. 落地推进阶段规划

| 阶段 | 周期 | 核心交付物 | 验收指标 |
| :--- | :--- | :--- | :--- |
| **Phase 1: 策展打分链路** | 1周 | 服务端 `asyncReviewImage` 合并打分 Prompt，落库 `ai_score` | 新上传 UGC 自动生成分数与评语，日志完整 |
| **Phase 2: 数据表与端云同步** | 3天 | Drift 表结构扩展 + `sys_db_sync` 增量同步兼容 | 客户端本地能查到 `ai_score` 与 `ai_reason` |
| **Phase 3: 客户端展现与探索混排** | 1周 | 遵循极简美学的微标签展示 + 20% 探索与利用混排算法 | 做题界面不增赘余容器，新内容曝光率显著提升 |
| **Phase 4: 闭环毕业与汰换验证** | 持续 | 沉淀毕业与淘汰数据看板，观察新 UGC 创作者留存 | 新内容破零周期缩短 80%，劣质高分内容淘汰率 100% |

## 4. 总结

该方案把 AI 的算力与理解能力用在**“信息冷启动分配”**这一最卡脖子的经济学困境上，既打破了既有内容的利益垄断，又坚守了“用户真实体验为终极标尺”的初心，且通过算法与架构上的“搭便车”设计，实现了**零新增重型服务、零多余做题容器、原生兼容离线同步**的优雅工程落地。
